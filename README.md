# نظام إدارة المستشفى — المرحلة الأولى (Core MVP)

نظام ويب لإدارة مستشفى متوسط الحجم (50–200 سرير)، مبني على أساس قياسي وقابل للتوسع
ليتولى تطويره لاحقًا أي شركة برمجة. هذه المرحلة الأولى تغطي **البنية الأساسية**:
تسجيل دخول وصلاحيات، ملفات المرضى، المواعيد، السجل الطبي المبسّط، والفوترة النقدية.

---

## 1. المعمارية التقنية

| الطبقة | التقنية | السبب |
|---|---|---|
| الواجهة الأمامية | React + Vite | سريعة، معيار صناعي، سهل توظيف مطورين لها |
| الترجمة/RTL | i18next | دعم عربي (افتراضي) + إنكليزي مع تبديل فوري للاتجاه |
| الخادم (Backend) | Node.js + Express | نفس بيئة نظام VII الحالي — منحنى تعلّم أقل لأي مطور يعرف الكود الحالي |
| قاعدة البيانات | PostgreSQL (بدل NeDB) | علائقية، تدعم القيود (constraints)، مناسبة لحجم بيانات مستشفى حقيقي وتقارير معقدة |
| ORM | Sequelize | يبسّط الترحيلات (migrations) ويقلل أخطاء SQL يدوية |
| المصادقة | JWT + صلاحيات حسب الدور (RBAC) | لا حاجة لجلسات على السيرفر، مناسب لعدة أجهزة/أقسام تتصل بنفس الخادم |
| النشر | Docker Compose | يسمح بتشغيل النظام كاملًا (قاعدة بيانات + خادم + واجهة) بأمر واحد على أي سيرفر داخل المنشأة |

**لماذا PostgreSQL بدل NeDB (المستخدمة في نظام VII)؟**
NeDB مناسبة لمركز صغير بعدد محدود من الأجهزة، لكنها ملف واحد بلا قفل معاملات (transactions)
حقيقي، وهذا خطر مع مستشفى 50-200 سرير وعشرات المستخدمين المتزامنين (تصادم في الفوترة
أو حجز الأسرّة). PostgreSQL توفر تكامل بيانات حقيقي وتستحمّل النمو.

## 2. الأدوار والصلاحيات (RBAC)

| الدور | الصلاحيات في هذه المرحلة |
|---|---|
| `admin` | كل شيء + إدارة المستخدمين والأقسام |
| `reception` | تسجيل مرضى، حجز مواعيد، إنشاء فواتير |
| `doctor` | عرض المرضى، كتابة السجل الطبي والتشخيص |
| `nurse` | عرض المرضى والمواعيد (توسّع في مرحلة التنويم) |
| `billing` | إدارة الفواتير والتسديد |
| `pharmacy` / `lab` / `management` | معرّفة في النظام كأدوار جاهزة، ستُفعَّل وظائفها في المرحلة القادمة |

## 4. التشغيل على السيرفر المحلي (on-premises)

### المتطلبات
- سيرفر (أو حاسوب مخصص) بداخل المستشفى بنظام Linux أو Windows مع Docker Desktop
- Docker + Docker Compose مثبّتين

### خطوات التشغيل

```bash
# 1. انسخ ملف البيئة وعدّل كلمات السر والمفاتيح
cp backend/.env.example backend/.env
# افتح backend/.env وغيّر DB_PASSWORD و JWT_SECRET إلى قيم حقيقية وسرّية

# 2. عدّل كلمة سر قاعدة البيانات في docker-compose.yml لتطابق backend/.env

# 3. ابنِ وشغّل كل الخدمات
docker compose up -d --build

# 4. أنشئ حساب المدير الأول والأقسام الافتراضية (مرة واحدة فقط)
docker compose exec backend npm run seed
```

بعد ذلك يكون النظام متاحًا على: `http://<عنوان-السيرفر-المحلي>`

بيانات الدخول الافتراضية بعد seed:
- اسم المستخدم: `admin`
- كلمة المرور: `ChangeMe123!` — **غيّرها فورًا من شاشة المستخدمين بعد أول دخول**

### النسخ الاحتياطي
قاعدة البيانات محفوظة في Docker volume باسم `hospital_db_data`. يُنصح بجدولة نسخ احتياطي
يومي تلقائي لهذا الـ volume (أو استخدام `pg_dump` مجدولة) لأن هذا هو مصدر البيانات الوحيد
في نظام on-premises بدون سحابة.

## 5. خارطة الطريق — المراحل القادمة

هذه المرحلة الأولى (الأساس) مصممة بحيث تُبنى عليها المراحل التالية دون إعادة هيكلة جذرية:

**المرحلة 2 — التنويم (Inpatient)**
- نماذج: `Ward` (جناح)، `Bed` (سرير)، `Admission` (دخول/خروج مريض)
- جولات الأطباء (Doctor Rounds) وملاحظات دورية
- تمريض بالورديات: تسجيل العلامات الحيوية الدورية، تسليم/استلام وردية
- غرف العمليات: جدولة، فريق الجراحة، تقرير العملية
- الطوارئ: نظام فرز (Triage) بالأولوية

**المرحلة 3 — الصيدلية والمخزون**
- مخزون أدوية بالكميات وتواريخ الانتهاء
- ربط الوصفة الطبية بصرف الأدوية تلقائيًا من المخزون
- تنبيهات نفاد المخزون

**المرحلة 4 — المختبر والأشعة**
- طلب فحص من الطبيب → نتيجة من المختبر → تظهر في ملف المريض
- رفع صور الأشعة (PACS بسيط أو أرشفة ملفات)

**المرحلة 5 — تقارير الإدارة العليا**
- لوحة تحكم: الإشغال، الإيرادات، عدد المرضى، أداء الأقسام

> ملاحظة أمنية مهمة قبل التشغيل الفعلي: هذا النظام يحتوي بيانات طبية حساسة.
> قبل الاستخدام الحقيقي يجب: (1) تفعيل HTTPS حتى داخل الشبكة المحلية، (2) مراجعة
> سياسة كلمات المرور، (3) تفعيل نسخ احتياطي مُشفّر، (4) مراجعة قانونية لمتطلبات
> حماية البيانات الصحية المعمول بها محليًا.
